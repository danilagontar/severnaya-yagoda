# Решения по пилоту «Северная ягода» (кейс 04)

Фиксируем то, о чём договорились, чтобы не обсуждать заново.

## Продукт
- Главный пользователь: бухгалтер. Реестр утверждает финансовый директор (П-9), поэтому система предлагает вердикт, а бухгалтер подтверждает.
- Сверку делает детерминированный код. LLM только извлекает поля из письма и формулирует тексты писем. Суммы всегда считает код.
- Без API-ключа извлечение работает на правилах; место подключения LLM явное.
- LLM-провайдер: **GigaChat API** (а не Claude), через серверный прокси. Подробности в `docs/llm.md`.
- Стек: React + Vite + TypeScript + Tailwind + shadcn/ui.

## Источники данных
- **Заказы из 1С:ERP**: поставщик, материал, цена, заказанное количество, закупщик. Приёмка на складе (принятое количество, дата) тоже из 1С:ERP (лист «Заказы и приёмка»).
- **Изменения к заказам в Directum RX**: согласования цены, количества, сроков поставки, допсоглашения о смене реквизитов (лист «Согласования»). Действует только подписанное, в своих границах (П-6).
- **Счета и письма**: общий почтовый ящик бухгалтерии.
- В интерфейсе и в симуляции событий источник называем явно: «приёмка из 1С:ERP», «согласование из Directum RX». В пилоте это срез из xlsx, в продукте интеграции.

## Вердикты (6)
оплатить, вопрос, вернуть, дубль / заменён, стоп, письмо (контекст к другому документу).

- В-13 и В-21 (в эталоне «⚠️/↩️»: цена выше заказа, согласование не действует по дате / по заказу) получают **«вопрос» закупщику**. Причина: согласование могли просто не оформить; возврат поставщику из-за внутренней недоработки портит отношения. Так же, как В-10.

## Интерфейс
- **Никаких эмодзи в интерфейсе.** Вердикты обозначаются текстом + значком из набора иконок (lucide) + цветом из палитры.
- **Без длинного тире «—».** Ни в текстах интерфейса, ни в документах. Вместо него двоеточие, запятая, точка или скобки; для переходов стрелка «→».
- **Без точки-разделителя «·».** Нигде: ни в интерфейсе, ни в документах. Поля в одной строке разделяет тонкая вертикальная черта (компонент `Sep`), в тексте запятая.
- Палитра: `docs/palette.md`. Светлая тема по умолчанию, тёмная включается переключателем.
- Очередь группируется по действию: «требует решения» → «к оплате» → «без действий».
- Карточка: колонки «Заказ (ERP) / Согласование / Приёмка / Счёт», явный пересчёт фасовки, связанные документы, «по заказу выставлено X из Y», правило и адресат (П-9).
- Новое письмо перепроверяет всю очередь (письмо о реквизитах переводит готовый счёт в «стоп»).
- «Не платить» (135 800 ₽) и «отложено до приёмки / ответа» (88 480 ₽): разные цифры, не складываются.
- Вкладка «Сверить с эталоном» сделана под пункт защиты «Данные и их проверка».
- В шапке показан срез данных (16.11.2026 12:00).

## Исправления после проверки сайта (13.11.2026)
- Счёт сверх заказа переводит в «вопрос» только сам себя; ранние счета в пределах заказа и приёмки остаются «оплатить» (пометка П-3 info).
- П-5 «предоплата» только тогда, когда часть счёта в пределах заказа ещё не принята. Если всё принятое уже выставлено, это лишний счёт (П-3), а не предоплата.
- «Задержано из-за реквизитов» (сверка пройдена, П-2) показывается строкой под «Отложено» и в «Отложено» не складывается: эталон 88 480 ₽ не меняется.
- Демо-письма: в данных кейса нет заказов со свободным принятым остатком, поэтому демо это исправленные счета или повторы существующих, а не «новые чистые» счета.
- Инструкции для GigaChat хранятся на сервере (server/prompts.ts); браузер шлёт только задачу и текст, плюс проверка Origin и не больше 20 запросов в минуту с адреса.
- «Дописать с ИИ»: только вступление и концовка, от первого лица, без слов с родом; при «стоп» ничего про оплату.

## Неожиданные письма (13.11.2026)
Прогон трудных писем, ошибки закреплены тестами в `src/core/hard-letters.test.ts`.
- «Стоп» по П-2 только на смену получателя или банка («новые реквизиты», «реквизиты изменились», «р/с 4070…», «сменился банк»). Просто слово «реквизиты» («указаны в счёте», «прежние») не останавливает оплату.
- Ответ над цитатой: читается только то, что написано сверху; цитата не включает «стоп» и не подменяет счёт. Если счёт есть только в цитате ответа поставщика, это повторная отправка (копия).
- Пересланное письмо («Пересланное сообщение», «От: …»): разбирается пересланная часть от имени её отправителя; в карточке пометка, кто переслал.
- Несколько счетов в одном письме: разбирается первый, письмо уходит в «вопрос» с перечнем номеров, остальные завести отдельно. Автоматически письмо на части не делим.
- Распознаются «Сч. 45», «счет номер 202», латинские буквы внутри русских слов, «ЗП-О8» / «3П-06», итог «к оплате», «15.000,00», «120 (сто двадцать) руб.». 20-значный расчётный счёт номером счёта не считается.
- Не решено: ИИ-разбор читает письмо целиком, вместе с цитатой, и может дополнить пустое поле числом из цитаты.

## Журнал событий и решения бухгалтера (14.11.2026)
- Состояние пилота = выгрузка кейса + журнал событий (`src/core/events.ts`): письма (почта), приёмка (1С:ERP), подписание согласований (Directum RX), решения бухгалтера, передача и утверждение реестра. Сверка (`reconcile.ts`) не меняется и считается заново по журналу. В продукте журнал переедет в базу и станет журналом действий.
- Решения: подтвердить в реестр, ждём ответа, оплатить по решению бухгалтера (сумма не больше счёта, причина обязательна; на «стоп» нельзя), возвращено поставщику, не платить, передано ФД и закупщику.
- В реестр попадают только подтверждённые счета и оплата по решению. Сверка лишь предлагает к оплате.
- Решение снимается само, если вердикт или сумма изменились (например, пришло письмо о смене банка). Передача реестра ФД действует, пока реестр тот же; если изменился, снова черновик.
- Ответ закупщика письмом вердикт не меняет (П-6): цена или количество меняются только подписанным согласованием в Directum RX.

## Сценарии для жюри и видимые изменения (14.11.2026)
- Вкладка «Проверить пилот» (до 14.11.2026 называлась «Сценарии»): события из учётных систем (симуляция) с предпросмотром «что изменится»: приёмка 200 коробов по ЗП-01 (В-07 → оплатить), приёмка 80 поддонов по ЗП-05 (В-17 → оплатить), подпись СГ-05 (В-10 → оплатить); демо-письма одним нажатием; журнал событий с «убрать»; «Отменить последнее» и «Сбросить демо».
- После любого события на плитках сводки на 4 с появляется разница («−8 000», «+1»), а плитка подсвечивается по смыслу и гаснет за 6 с: стало лучше зелёным, хуже красным, «Не платить» и «Отложено» жёлтым без оценки. Для писем, сценариев и отмены показывается баннер с изменившимися вердиктами и «отменить последнее» (над правой областью, очередь не сдвигает).
- Своё письмо вставляется формой во вкладке «Проверить пилот» (отдельной кнопки в шапке нет: бухгалтер письма не пишет). В продукте письма приходят из почты сами.
- В карточке есть «История заказа»: заказ и приёмка (1С:ERP), согласования (Directum RX), счета и письма (почта) по дате; события журнала в конце с пометкой «симуляция».
- Приёмка по ЗП-01 делает к оплате В-07 (счёт на 1 000 шт), а не В-23: по заказу на 1 000 шт выставлено 1 200, В-23 остаётся вопросом.
